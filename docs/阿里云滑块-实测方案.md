滑块验证（阿里云 NoCaptcha「访问验证」）——实测方案与结论
========================================================

一、结论先说
--------------------------------------------------
1) 组卷网这一层是 **aliyun Captcha 2.0 的 sliding 组件，无缺口拼图**：
   页面上只有一条轨道 + 一个橙色把手，文案「请按住滑块，拖动到最右边」。
   → 不需要算缺口位置，答案就是"拖到底"；要骗过的是**行为风控**，不是几何题。
2) 开源"解滑块"方案依旧没有能直接用的（slider-captcha-lab 明确放弃阿里云这一款），
   **但"自己的插件里做拟人拖拽"是可行的**，实测能拿到「验证通过」。
3) stealth 浏览器（patchright / camoufox）在组卷网这层**没有额外收益**：
   A/B 实测 patchright 有界面 ≈ 我们的零依赖 CDP 启动器有界面（都拿到正常页），
   两者无窗口都直接吃「阻断页面」。差别在"有没有界面 + profile 干不干净"，不在库。

二、这轮实测出来的三条硬约束（真正的坑）
--------------------------------------------------
1) **事件必须是可信事件**：JS 合成的 `new MouseEvent` 是 `isTrusted=false`，
   阿里云直接判死。必须走 CDP `Input.dispatchMouseEvent`（内核输入管线发出的）。
2) **页面必须有焦点**：窗口被别的程序压住时，内核会**静默丢弃
   `mousePressed`/`mouseReleased`**，只有 `mousemove` 能到页面。
   症状极具欺骗性：滑块看得见、鼠标轨迹也画出来了，但把手纹丝不动。
   现场抓到的证据：`document.hasFocus()=false` 时页面只收到 `pointermove`，
   `pointerdown` 数量为 0。
   解法：
   - `Emulation.setFocusEmulationEnabled {enabled:true}`；
   - 还不够就在页面空白处点一下把焦点抢过来；
   - 拖之前先"试推 8px"看填充条是否 >0，没生效就松手重按（最多 3 次）。
3) **通过之后不要重新导航**：验证成功后 WAF 会在 1~2 秒内把当前页**自己回跳**到
   目标地址。此时再 `goto` 一次会被当成新的高风险请求，立刻又弹验证
   （这就是上一轮"拖完还是被拦"的真凶之一）。
   正确做法：通过 → 等它自己回跳（`waitCaptchaCleared`）→ 在当前页继续干活。

三、实现（`lib/slider.mjs` + `lib/site.mjs` + `lib/cdp.mjs`）
--------------------------------------------------
- DOM 选择器（站点固定）：
  `#aliyunCaptcha-sliding-body` 轨道 320×40、`#aliyunCaptcha-sliding-slider` 把手 40×40、
  `#aliyunCaptcha-sliding-left` 填充条、`#aliyunCaptcha-sliding-text` 文案。
- 轨迹：easeInOutCubic（起步慢/中段快/收尾减速）+ 每帧 6~18ms + y 轴 ±1.6px 抖动
  + 偶发 30~90ms 微停顿 + 末段顶过右墙 2~5px 再回正 + 松手前停一拍。
  拖之前在页面上随意晃 6~11 次（真实用户进验证页不会一秒内直奔把手）。
- 派发：`mouseFire()` 不发等回执（WebSocket 保序），否则 67 帧会被 70ms/次的 RTT
  拖成 6.4 秒 —— 实测那种"慢速匀速"更容易被判 F001。
- 失败处理：站点返回 `VerifyCode=F001 / VerifyResult=false` 时把手不复位，
  插件自动重载验证页换新挑战再试（`captchaAttempts`，默认 3）。
- 接线：`site.go()` 与 `searchViaFetch()` 撞验证时自动 `passCaptcha()`，
  通过后等自回跳再继续；`zujuan_captcha` 默认先自动、失败才开人工窗口。

四、实测数据（2026-11-17 凌晨，同一 profile）
--------------------------------------------------
- `dev/slider-lab.mjs` 逼验证：24 次慢速导航不触发；120ms 间隔连点第 21 次触发
  → 说明阈值在"请求密度"，把节奏控住比什么技巧都省事。
- 手势级（`pointerdown` 确实进了页面）统计：11 次拖拽 5 次拿到「验证通过」（约 45%）。
  失败回包固定是 `VerifyCode=F001 / VerifyResult=false`。
  → 所以策略不是"一次拖准"，而是"失败就换新挑战再拖"，`captchaAttempts=3` 时
  单次调用（≤3 次重试）5 次实测里 4 次拿到放行。
- 端到端（`dev/e2e-blocked.mjs`）：`go()` 自动过验证 → 自回跳 → 正常页；
  随后知识点检索再撞验证 → 重试后过 → 10 道题；关键词检索（页面内 fetch）不再触发验证。
- 反例（值得记住）：无焦点、或 CDP 等回执拖 6.4 秒、或通过后又 `goto` 一次，
  三种都会让"看起来拖成功了"但站点仍判失败 / 仍拦。

五、窗口可见性（要"不弹窗"就得知道这条）
--------------------------------------------------
需求是"别在桌面上弹窗"，但站点又不接受无窗口。实测结论：
- `--window-position=-32000,-32000` **经常被 profile 记住的窗口位置覆盖**（连上后一看又回到 0,0），
  必须连上 CDP 后再 `Browser.getWindowForTarget` + `Browser.setWindowBounds` 显式挪一次；
- 窗口挪到屏幕外后，**渲染会被节流**：鼠标轨迹发涩，屏幕外连拖 3 次全被判 `F001`；
  把窗口挪回屏幕内，同样轨迹第 2 次就「验证通过」；
- 所以最终策略：**平时屏幕外（不打扰），只在拖滑块那一步 `showWindow()`，拖完 `hideWindow()`**。
  扫码登录同理——只有你亲自操作的那几秒才把窗口挪回来。
- Chrome 自己的弹窗也一并压掉：`--disable-session-crashed-bubble`、`--hide-crash-restore-bubble`、
  `--disable-search-engine-choice-screen`、`--no-service-autorun`、`--password-store=basic`。

六、被拦成"每个页面都弹验证"了怎么救（实测）
--------------------------------------------------
`zujuan_profile({action:"clean"})`（等价脚本 `dev/profile-clean.mjs`）：
只删风控类 Cookie（`alicfw` / `acw_tc` / `acw_sc__v2` / `aliyungf_tc` / `_c_WBKFRo` / `HMACCOUNT` …）
并清 localStorage/sessionStorage，保留登录态（`user_token` / `UT1` / `UT2` / `TGC` / `refresh_token` …）。
实测：删掉 9 个风控 Cookie 后立刻恢复正常（复访 `captcha=false`，直接出频道页）。
如果洗过还拦，判定就已经落在服务端（IP/设备），换网络（手机热点）最省事。

七、仍然推荐的做法（省事优先）
--------------------------------------------------
1) 别硬撞：`blueprintSiteBudget`（默认 8）、`paceMs`、页面内 fetch 检索、本地题库优先；
2) 撞了就让它自动拖（默认开），失败再 `zujuan_profile({action:"clean"})` 洗风控 Cookie；
3) 换网络（手机热点）依然是最省力的一招，尤其是同一 IP 连着被拦时；
4) 攒题按天进行：题库累积（`kp:<考点>` 标签）比"一小时冲完"划算得多。
